# Hosting Guide

This dashboard is a **fully static website**. A build produces a `dist/` folder of
plain HTML, JavaScript, CSS, and JSON; hosting it means serving those files. There
is no server-side code, no database, no API keys, and nothing to run or patch at
runtime — any static file host works (GitHub Pages, Netlify, Cloudflare Pages,
AWS S3 + CloudFront, Azure Static Web Apps, or a plain nginx/Apache directory).

## Quick start: host a prebuilt `dist/`

If your delivery bundle includes a prebuilt `dist/`, upload its contents to your
host and you are live — no build step needed.

One caveat: a build is tied to the URL path it was built for (the *base path*,
see `VITE_BASE` below). A prebuilt `dist/` made for `https://host/` will not work
at `https://host/some-path/`, and vice versa. If your URL layout differs from the
prebuilt one, rebuild from source — it takes about a minute.

## Building from source

Requirements: **Node.js 22** (see `.github/workflows/deploy-pages.yml` for the
reference version) and npm.

```bash
npm ci                 # install exact locked dependencies
npm run build          # -> dist/
```

If the site will be served from a subpath rather than the domain root, set the
base path at build time:

```bash
VITE_BASE=/my-subpath/ npm run build
```

The build runs two automatic gates:

- **prebuild** (`scripts/sync_web_data.mjs`) copies the `viewstore/` data snapshot
  into `public/data/` and fails loudly if a data file is missing, malformed, or
  has an unexpected schema version.
- **postbuild** (`scripts/check_bundle.mjs`) verifies the compiled JavaScript
  contains no individual-level data fields and stays within its size budget.

## Verifying a build

```bash
npx playwright install chromium    # one-time; on a fresh Linux host add --with-deps
npm run verify
```

`npm run verify` serves the built `dist/` locally and drives a headless browser
through every geography × sector × cohort combination the dashboard can display
(~280 views), asserting nothing errors and no malformed value reaches the screen.
Run it after every build and after applying a data refresh. If the build used a
`VITE_BASE`, run verify with the same value.

## Configuration reference

Both are **build-time** environment variables — they are compiled into the output,
so changing them means rebuilding. There is no runtime configuration.

| Variable | Default | Effect |
| --- | --- | --- |
| `VITE_BASE` | `/` | URL base path the site is served under. Must match the deployment path exactly, with leading and trailing slashes. |
| `VITE_REPORT_DOCX` | unset | Set to `1` to show the report-download button in the header. Requires the report `.docx` to be present in `public/` before building. |

## Serving notes

- The app is a single page (`index.html`); it uses no client-side routing, so no
  rewrite/fallback rules are needed on the host.
- Data files under `dist/data/` are fetched at runtime with a version query string
  derived from the data vintage, so aggressive CDN/browser caching is safe — a
  data refresh will not be masked by stale caches.
- The included `.github/workflows/deploy-pages.yml` is a complete, working GitHub
  Pages deployment (build → verify-gates → publish). Use it as-is on GitHub, or as
  a reference for wiring the same steps into another CI system.

## Data refreshes

The figures live in `viewstore/*.json` — precomputed aggregates generated by the
Burning Glass Institute's analysis pipeline. Refreshes are delivered by BGI
(roughly annually) as a complete updated snapshot of this repository, since the
app and its data are versioned together. Do not hand-edit `viewstore/` files; the
prebuild gate validates their structure but cannot validate the figures.

To apply a refresh: replace the repository contents with the delivered snapshot
(or merge the delivered commit), then `npm ci && npm run build && npm run verify`
and redeploy `dist/`.
